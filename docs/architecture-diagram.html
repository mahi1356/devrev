How the devrev pieces work together

One task goes in, three rounds of developer/reviewer back-and-forth happen against a local Ollama model (every exchange logged to disk), and the result gets checked against QuixBugs' own test suite before the fixture is put back exactly as it was found.

  1. Pick a program. fix_one(name) reads the buggy source from python_programs/<name>.py (or the harness loops this over all 40).
  2. Hand it to the agent loop. main_orthestrator.run(task, code=buggy_source) starts a fresh ConversationLogger and begins round 1.
  3. Developer writes a fix. DeveloperAgent calls Ollama with the task, current code, and any prior reviewer feedback; the exchange is logged.
  4. Reviewer critiques it. ReviewerAgent calls Ollama on the same code and either points out issues or replies APPROVED; also logged.
  5. Loop or exit. If the reply contains "APPROVED" the loop stops; otherwise the critique feeds back into another developer round, up to 3 rounds total.
  6. Extract the code. extract_code() regex-pulls the final ```python fence out of the last reply; no fence means an automatic FAIL.
  7. Swap into the fixture. The fix is written over the real python_programs/<name>.py so QuixBugs' own tests can import it.
  8. Run the real tests. pytest runs test_<name>.py under a 30s timeout (unfixed bugs can infinite-loop).
  9. Restore the fixture. A finally block rewrites the original buggy source back, win or lose.
  10. Record the result. PASS/FAIL is printed per program and rolled up into an N / 40 total.

The loop

  • main_orthestrator.py alternates DeveloperAgent.run() and ReviewerAgent.run(), feeding each critique back in as the next round's feedback.
  • Both agents are the same local model (qwen2.5-coder:7b) with different system prompts — one instructed to write/fix, one to critique or approve.
  • ConversationLogger writes every raw request/response pair to logs/<timestamp>.json, rewriting the file after each round so a killed run still leaves a partial trace.
  • Ollama must already be running on 127.0.0.1:11434 — the start-ollama skill checks and starts it.

The fixture pass

  • QuixBugs' tests import python_programs.<name> directly, so the harness overwrites that file in place rather than passing code around in memory.
  • A 30-second subprocess timeout exists because some QuixBugs bugs are genuine infinite loops, not just wrong answers.
  • The original buggy file is restored in a finally block, so a run never leaves the dataset modified.
Known gap: the loop only breaks early on the literal substring "APPROVED" in the reviewer's reply. The model sometimes writes "Approved" instead, which the check misses — the loop then just runs out its 3 rounds instead of stopping early.
